# 何时不该用 Agent：ResearchOps 的工作流对照

在本组 **16 个内部已知任务**的受控观察中，固定工作流 16 项通过且没有模型调用；Agent 路径为 13 项通过、1 项失败、2 项未知。这支持把固定工作流作为这组任务的默认实现，尚未证明 Agent 在未知任务上的优势。

| 路径 | 任务数 | 通过 | 失败 | 未知 |
| --- | ---: | ---: | ---: | ---: |
| 固定工作流 | 16 | 16 | 0 | 0 |
| Agent | 16 | 13 | 1 | 2 |

两项未知保留在 16 题分母内，不计作通过，也不改记为失败。固定模板的解析优势、工具故障与模型能力的归因需分别讨论。任务、评分口径、发布锚点与验证限制见 [Main51 受控观察证据](evidence/main51-controlled-observation-v1/README.md)。

## 这个项目解决什么问题

ResearchOps 将科研分析拆成可复核的步骤：检查数据、验证显式研究设计、选择方法、计算统计量、生成聚合证据，并在发布前等待人工审批。固定工作流和 Agent 编排都必须遵守工具与证据边界；模型不能自由执行 Python、SQL 或 shell。

当输入结构、工具顺序和异常分支可以预先定义时，固定工作流已经可以完成任务。引入 Agent 的理由应来自需要动态判断的工作，并通过独立评测检验；不能从“接入了模型”推导出任务质量更高。

## 三个可检查的工程选择

- **计算与编排分开。** ANCOVA、Welch 检验及聚合图由确定性工具生成；结论通过 evidence ID 和数值路径回查。研究设计缺失时停止，不从列名补全统计假设。
- **权限在执行边界检查。** 模型使用逻辑资源 ID；未知工具与越权访问被拒绝。发布批准绑定调用参数、工具与策略版本、源证据哈希，恢复执行时重新校验。
- **失败与未知留在记录中。** 评分区分通过、失败和未知，审计记录工具调用与审批。哈希链可以发现内容变化，但没有外部签名时不能保证数据库管理员无法重建账本。

设计与实现入口见 [架构说明](ARCHITECTURE.md)；攻击面、现有控制和未覆盖项见 [安全边界与 OWASP 对照](SECURITY_OWASP.md)。

## 如何查看和复核

先按 [离线演示](DEMO.md) 查看模拟数据、聚合分析与审批流程，再对照 [Main51 受控观察证据](evidence/main51-controlled-observation-v1/README.md) 阅读两条路径的结果。演示、组件回归和 Agent 任务观察各有自己的口径，不能互相替代。

仓库是研究原型。已知任务上的结果不证明未知任务泛化、独立专家验证或生产可靠性；模拟数据分析也不构成临床使用依据。历史评测与声明边界集中在 [证据索引](EVIDENCE.md) 和 [项目状态](../STATUS.md)，不将不同版本的成绩拼成当前能力。
